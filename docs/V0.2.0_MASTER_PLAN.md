# v0.2.0 Master Plan — `ai-dev-team-marketplace`

Status: **APPROVED WITH ADJUSTMENTS — 2026-09-01.** Base: `v0.1.0` (GitHub release published 2026-09-01, PR #1 merged into `main` at `dc088c8`).

## APPROVAL ADJUSTMENTS (applied throughout this document)

Human review approved this plan with four adjustments, formalized in [ADR 0004](adr/0004-v0.2.0-scope-and-consolidation.md) and [ADR 0005](adr/0005-database-migration-safety-model.md):

1. **`planning-deployment` moves from P1 to P0.** All four "existing agent, no dedicated skill" gaps (`database-engineer`, `qa-engineer`, `solution-architect`, `release-manager`) close in the same release.
2. **ADR 0005's database safety model distinguishes AUTHOR/EDIT/REVIEW of a local migration** (LEVEL 2 — reversible, no extra confirmation) **from EXECUTE/APPLY against a real database.** Execution against a demonstrated-disposable local/test target (LEVEL 3) may be carried out by the skill itself once disposability evidence exists; execution against any shared/staging/production target (LEVEL 4) is **never** carried out by the skill — it stops and a human executes separately, not "the skill executes after confirmation." DROP/data-loss/production-RLS/destructive-backfill (LEVEL 5) always require explicit human confirmation regardless of environment, including on a demonstrated-disposable local/test target. ADR 0005 also records that the LEVEL 5 "always gated, even in disposable local/test" guarantee is **not yet runtime-enforced**: `enforcing-safety-baseline` v0.1.0 still exempts destructive operations on a disposable local/test database from confirmation, and PR #3 must close that gap (plus land the four regression cases ADR 0005 specifies) before `managing-database-migrations` is considered complete. Five levels total — see ADR 0005.
3. **The DevSecOps extension to `auditing-security` (P0 item 5) does not become a homegrown SAST/SCA engine.** Its own automation is limited to deterministic checks; dependency-vulnerability detection defers to real ecosystem tooling where available, reporting evidence and limitations rather than a bespoke vulnerability database.
4. **PR sequence consolidated** from eight PRs to six, grouped by delivery concern — see the updated PR SEQUENCE section below.

No code, skill, agent, or manifest-version change has been made as part of producing PR #2 (this document plus the two ADRs plus `ROADMAP.md`) — those land in the PRs that follow, per the sequence below.

## EXECUTIVE SUMMARY

v0.1.0 shipped a deliberately small, eval-covered plugin: 10 user-facing skills + 1 internal safety-baseline skill, 10 role-scoped agents, a stdlib-only validator, CI wired to both the local validator and the official `claude plugin validate`, and 3 ADRs recording the architecture's hardest decisions (multi-plugin marketplace shape, agent safety-preload model, plugin packaging self-containment).

v0.2.0's job is to close the highest-value gaps the v0.1.0 ADRs and ROADMAP already flagged, **without** repeating the one mistake those ADRs explicitly warn against: "It would be easy to ship 40–100 shallow, near-duplicate skills… New families should become new plugins… rather than bloating `ai-dev-team` into a monolith" (ADR 0001).

Applying that discipline to the 12 requested families produces a small delivery:

- **4 new skills, all P0** (test authoring, database/migration safety, architecture review, deployment planning) — each fills a real gap where an *agent already exists* (`qa-engineer`, `database-engineer`, `solution-architect`, `release-manager`) but has no skill of its own to point at, currently riding generically on `implementing-features`/`planning-implementation` or, for `release-manager`, on release-readiness verification alone. `planning-deployment` was promoted from P1 to P0 on review — see APPROVAL ADJUSTMENTS above.
- **Zero new agents.** Every family maps onto an existing agent; growing the agent roster is a bigger structural cost (tool-scoping, safety-preload wiring, namespacing) than growing the skill roster, and v0.2.0 should prove the "new skill on an existing agent" pattern before considering a new agent.
- **Several targeted extensions** to existing skills (`auditing-security`, `continuing-project-work`, `orchestrating-development-team`) instead of new skills, where the new capability is a natural superset of what the skill already does.
- **Two families found to be mostly duplicates** of existing plugin behavior or the Claude Code harness itself (PR-description authoring is already a built-in harness capability; most of "GitHub Engineering" and "Frontend/Mobile framework depth" are explicitly non-goals in ADR 0001/ROADMAP) — flagged `DO NOT BUILD YET` with the specific reason, not just deprioritized.

No compatibility break: all v0.2.0 work is additive to the 10 existing skills and 10 existing agents. Their `name` frontmatter, directory paths, and public behavior are untouched.

**Packaging restriction (hard constraint for everything below)** — every runtime file under `plugins/ai-dev-team/` must resolve entirely within that directory once copied out alone (ADR 0003). No new skill/agent/reference may link `../../` upward to repo-root docs for anything runtime-load-bearing; only pure human-facing navigation (README/CHANGELOG) may use absolute GitHub URLs.

**Runtime findings already documented** — the `claude plugin validate --strict` gaps this repo's own validator exists to cover (empty `description` passes, invalid skill `name` passes, dangling `skills:` preload target passes, cross-plugin-root link escape passes) are recorded in `token-efficiency.md`'s comparison table and must be assumed to still apply to any new skill/agent v0.2.0 adds — i.e., `scripts/validate.py` is still the actual authority for these specific checks, not the official CLI.

## NEW SKILLS (full spec)

### 1. `managing-database-migrations`
- **Purpose:** Design, review, and safely author schema changes and migrations (PostgreSQL-first, Supabase-aware), including RLS policy review and online-migration safety patterns.
- **Trigger examples:** "diseña la migración para añadir X", "revisa este cambio de schema", "audita las políticas RLS de esta tabla", "necesito una migración segura para producción".
- **When NOT to use:** Pure query-performance tuning with no schema change (stays generic `implementing-features`/`debugging-systematically` territory unless it becomes its own P1/P2 item); non-Postgres/non-relational stores are out of scope for v0.2.0 — skill must detect and say so rather than guess.
- **Dependencies:** `references/stack-detection.md` (existing), new `references/database-safety.md` (online-migration patterns, RLS checklist, Supabase-specific gotchas), links `enforcing-safety-baseline`.
- **Agent mapping:** `database-engineer` (existing agent, `tools: Read, Edit, Write, Glob, Grep, Bash, Skill` unchanged) — its system prompt gains a named pointer to this skill, replacing the current generic fallback.
- **Tools:** none new; the skill itself needs no bundled script for v0.2.0 (migration authoring is judgment-heavy, not deterministic — per `token-efficiency.md`'s "open a reference vs. run a script" rule).
- **Safety implications:** governed by [ADR 0005](adr/0005-database-migration-safety-model.md)'s five-level model. Authoring/editing a migration file (LEVEL 2) needs no confirmation. Execution against a demonstrated-disposable local/test target (LEVEL 3) may be carried out by the skill itself once disposability evidence exists. The skill **never executes** against a shared, staging, or production target (LEVEL 4) — human execution required, the skill stops before execution, exactly like the existing deploy/force-push/hard-reset gate; "after confirmation the skill executes" is not the contract. `DROP`/`TRUNCATE`/destructive `ALTER`/irreversible backfill/production RLS changes/mass `UPDATE`/`DELETE`/schema reset/lossy rollback (LEVEL 5) always require explicit human confirmation regardless of environment, including on a demonstrated-disposable local/test target. ADR 0005 flags that this LEVEL 5 guarantee is **not yet enforced** by `enforcing-safety-baseline` v0.1.0 (it currently exempts destructive operations on a disposable local/test database) — PR #3 must update the baseline and land the four regression cases ADR 0005 lists before this skill is complete.
- **Eval strategy:** ≥3 scenarios: (a) a migration that drops a column with live traffic — must flag data-loss risk and require an online-migration pattern; (b) an RLS policy that leaks cross-tenant rows — must flag as BLOCKER-equivalent; (c) a clean, safe additive migration — must not manufacture findings.
- **Token-efficiency strategy:** detailed Postgres/Supabase/RLS checklist content lives in `references/database-safety.md`, not inline, so the `SKILL.md` body stays under the 250-line target; only loaded when the skill is actually invoked, per the existing 3-tier model.
- **Overlap:** none with `auditing-security` (that skill covers RLS from an *attacker/tenant-isolation-verification* angle at review time; this skill covers RLS from an *authoring/design* angle) — the two should cross-link, not merge, since their trigger contexts differ (build-time vs. review-time).

### 2. `writing-automated-tests`
- **Purpose:** Author and review unit and integration tests (explicitly not E2E — that stays `testing-with-playwright`'s job), including test-gap analysis and a coverage strategy recommendation.
- **Trigger examples:** "escribe tests unitarios para X", "añade tests de integración para el módulo Y", "qué falta de cubrir en tests aquí", "necesito una estrategia de coverage para este servicio".
- **When NOT to use:** End-to-end/browser flows (route to `testing-with-playwright`); a trivial one-line fix where `implementing-features`'s own "updated tests" exit criterion already suffices without invoking a separate skill.
- **Dependencies:** `references/stack-detection.md` (to detect the project's existing test framework/runner instead of assuming one), links `enforcing-safety-baseline`.
- **Agent mapping:** `qa-engineer` (existing agent) — gains this as its primary named skill alongside `testing-with-playwright`, since its description already says "Writes and runs automated tests (unit, integration, E2E/Playwright)" — the agent's remit already implied this skill existed; it didn't.
- **Tools:** no new tools; runs the project's existing test command via `Bash` (already granted).
- **Safety implications:** low — read/write to test files only, no irreversible actions; still links the baseline for evidence discipline (never claim "tests pass" without actually running them).
- **Eval strategy:** ≥3 scenarios: (a) new business logic added with zero tests — must flag the gap and propose concrete test cases, not just say "add tests"; (b) a function with an untested edge case (e.g. empty input, boundary value) — gap analysis must name the specific missing case; (c) tests that pass but only assert on mocks with no real integration coverage — must flag as a coverage-strategy weakness, not accept at face value.
- **Token-efficiency strategy:** framework-detection logic reused from `references/stack-detection.md` rather than restated; skill body focuses on decision criteria (unit vs. integration boundary, when a mock is appropriate vs. a real dependency) rather than framework-specific syntax examples.
- **Overlap:** `testing-with-playwright` (E2E only, explicitly distinct layer — SKILL.md must state the boundary explicitly to avoid the two being invoked for the same request); `implementing-features` (which already requires "updated tests" as an exit criterion — this skill is what implementing-features should *delegate to* for anything beyond trivial, not a competing path).

### 3. `reviewing-architecture`
- **Purpose:** Generate ADRs, review architecture/module boundaries, analyze technical debt and scalability risk, and recommend modularization — for existing systems or a proposed design.
- **Trigger examples:** "genera un ADR para esta decisión", "revisa la arquitectura de este módulo", "analiza deuda técnica aquí", "esto va a escalar si...", "cómo deberíamos modularizar X".
- **When NOT to use:** A single well-understood implementation with no genuine design fork (stays in `planning-implementation`, which already optionally delegates to `solution-architect` for "a genuine design decision" — this skill is what that delegation should land on, not a parallel path); don't invoke for style/naming preferences.
- **Dependencies:** `references/stack-detection.md`, links `enforcing-safety-baseline`; may read existing `docs/adr/*.md` in the target repo to match its own ADR-numbering/format convention rather than impose this marketplace's.
- **Agent mapping:** `solution-architect` (existing agent) — same "agent existed without a dedicated skill" gap as `database-engineer`.
- **Tools:** no new tools.
- **Safety implications:** none directly (advisory/documentation-producing skill); should explicitly *not* be the skill that executes a modularization refactor — that's `implementing-features`'s job once the plan is accepted.
- **Eval strategy:** ≥3 scenarios: (a) request for an ADR on a decision already made informally in chat — must produce Context/Decision/Consequences structure, not just restate the chat; (b) a module with circular dependencies — must be flagged as a structural finding, not missed; (c) a request to review architecture where the codebase is genuinely fine — must not manufacture a "modularize this" recommendation just to appear thorough (same anti-padding principle already proven in `reviewing-code`'s eval set).
- **Token-efficiency strategy:** this skill is exactly the kind ADR 0001 calls out as needing to stay optional/on-demand — `orchestrating-development-team`'s PLAN stage invokes it only for a genuine design decision, never as a default step, so its cost is paid only when the task actually warrants it.
- **Overlap:** `planning-implementation` (scope/impact planning for a *specific* change — this skill is for the *decision* underneath a class of changes, or a standing review of what already exists); `reviewing-code` (diff-level correctness/security findings, not architecture-level module-boundary findings — the two should be composable, not merged, matching the existing pattern where `orchestrating-development-team`'s REVIEW stage already runs `reviewing-code` and, conditionally, `auditing-security` together).

### 4. `planning-deployment` (P0 — promoted from P1 on review, see APPROVAL ADJUSTMENTS)
- **Purpose:** Produce a platform-aware deployment plan (Vercel, Docker, VPS, or a detected equivalent) covering rollback strategy, health checks, and post-deploy verification steps — planning only, never executing.
- **Trigger examples:** "cómo despliego esto en Vercel", "plan de rollback para este release", "necesito health checks para este deploy", "prepara el despliegue en el VPS".
- **When NOT to use:** Release-readiness verification itself (that's `preparing-releases`, which this skill's plan should be handed to as a precondition, not replace); no deployment target detectable in the repo — say so rather than assume a platform.
- **Dependencies:** `references/stack-detection.md` extended to also detect deployment config (`vercel.json`, `Dockerfile`, `docker-compose.yml`, CI deploy jobs), links `enforcing-safety-baseline`.
- **Agent mapping:** `release-manager` (existing agent) — gains this as a second named skill alongside its release-readiness remit.
- **Tools:** no new tools; explicitly must not gain any tool that could execute a real deploy (`release-manager`'s tool list stays `Read, Glob, Grep, Bash, Skill` — `Bash` here is for read-only inspection of deploy config, and the skill's own Decisions section must state that any deploy/rollback *command* it proposes requires separate explicit human execution, consistent with `release-manager`'s existing "never deploys or merges without separate explicit human confirmation").
- **Safety implications:** highest of the P0 items alongside `managing-database-migrations` — must inherit the existing irreversible-action confirmation gate verbatim, not redefine it.
- **Eval strategy:** ≥3 scenarios: (a) request to deploy with no rollback plan considered — must produce one, not skip it; (b) a platform with no health-check endpoint detected — must flag the gap rather than assume one exists; (c) a request that implies "just do it" — must still stop at the plan and name the confirmation step required, never simulate having deployed.
- **Token-efficiency strategy:** platform-specific checklists (Vercel vs. Docker vs. VPS) live in a reference doc keyed by detected platform, so a Vercel-only project never loads Docker-specific content.
- **Overlap:** `preparing-releases` (readiness gate vs. this skill's deploy mechanics — sequential, not duplicate: readiness must pass before a deployment plan is actionable).

## VALIDATION STRATEGY

- `scripts/validate.py` needs **no structural changes** for the P0 skills — they follow the existing 3 supported frontmatter shapes and existing directory conventions. It does need re-running against the new files to confirm: name/directory match, `enforcing-safety-baseline` link present, eval coverage ≥3 per new (plugin, skill) pair, no runtime link escaping `plugins/ai-dev-team/`.
- If the DevSecOps extension bundles a script under `plugins/ai-dev-team/scripts/`, that's a **new directory** the validator and the ADR-0003 copy-simulation test don't currently know to check for executability/self-containment — confirm `test_plugin_is_self_contained_when_copied` covers arbitrary files under the plugin root generically (expected yes, since it copies the whole directory) rather than assuming.
- Every new/modified `agents/*.md` file must keep `skills: [enforcing-safety-baseline]` and add the new skill only as a *named pointer in the system prompt body* + `Skill` tool access — never add it to the `skills:` preload list, to preserve the "safety baseline is the only unconditional preload" rule from ADR 0002/token-efficiency.md.
- `claude plugin validate . --strict` and per-plugin strict validation must both pass in CI for every new file — remembering, per `token-efficiency.md`'s own table, that the official CLI does **not** catch empty descriptions, invalid names, dangling skill-preload targets, or packaging-boundary escapes, so `scripts/validate.py` remains the actual gate for those.

## RUNTIME TEST STRATEGY

- Each new skill gets at least one **manual runtime invocation** against a real (or realistic fixture) repo before merge — not just an eval-file review — with the transcript or key evidence noted in the PR description, matching this repo's existing culture of "confirmed empirically" / "verified locally" claims in ADR 0002/0003 rather than assumed-correct.
- `managing-database-migrations` specifically needs a runtime smoke test against a fixture repo with an actual Postgres/Supabase migration directory, verifying it does **not** attempt to run the migration against a shared/staging/production-shaped target and does surface the rollback/RLS considerations — plus, once PR #3 lands the required `enforcing-safety-baseline` update (see ADR 0005), the four regression cases ADR 0005 specifies (additive-on-disposable needs no confirmation, destructive-on-disposable needs confirmation, shared/staging/production is never executed by the skill, local authoring needs no confirmation).
- `planning-deployment` needs a runtime smoke test confirming it never proposes running a deploy command as if it were already executed, and stops at the plan.
- Re-run the ADR-0003 packaging-boundary copy-simulation test after every new file is added, not only at the end — cheap to run, and it's exactly the check that caught a real P1 blocker in v0.1.0's own history.
- Full CI pipeline (`validate.yml`) must stay green after every individual PR in the sequence below, not just the final one — no PR should merge with a red validator or a red official `claude plugin validate --strict`.

## RISKS

- **Skill-bloat creep** — mitigated by ADR 0004 recording *why* each DO NOT BUILD YET item was excluded, so a future contributor can't quietly re-propose the same mega-skill without addressing the recorded reason.
- **Database-migration skill proposing something destructive** — mitigated by ADR 0005's five-level safety model, which keeps authoring/editing a local migration file confirmation-free (LEVEL 2), never lets the skill execute against a shared/staging/production target at all (LEVEL 4 — human execution required, skill stops before execution), and requires explicit human confirmation unconditionally for any DROP/data-loss/production-RLS/destructive-backfill operation regardless of environment (LEVEL 5) — plus a dedicated eval scenario for a destructive migration. **Not yet closed:** the LEVEL 5 guarantee needs a corresponding `enforcing-safety-baseline` update in PR #3 (see ADR 0005's REQUIRED PR #3 CHANGE) before it's actually runtime-enforced; this risk stays open until that lands.
- **Database-migration skill conflating "author" with "apply"** — a migration file existing in the repo, even merged, must never be reported as having been run; mitigated by ADR 0005 stating this distinction explicitly and by the evidence rule in `enforcing-safety-baseline` (no "migration successful" claim without having actually executed it against the specific target).
- **DevSecOps script false positives/negatives across ecosystems** — must report findings as "detected via `<tool>`, verify manually," never as a hard pass/fail verdict, consistent with `auditing-security`'s existing "confirmed / likely / hardening" classification model.
- **Packaging-boundary regression** — any new file with a stray `../../` link silently reintroduces the exact bug ADR 0003 fixed; mitigated by re-running the copy-simulation test after every new file, not just at the end of the cycle.
- **Token-budget regression in `orchestrating-development-team`** — adding 4 more skills to the pipeline table risks the orchestrator defaulting to invoking all of them "to be thorough"; mitigated by making the token-budget rule explicit and testing it with an eval scenario for a small, single-discipline change that should *not* trigger the new skills.
- **Backward compatibility** — no existing skill's `name`, directory path, or `SKILL.md` public behavior may change in a way existing evals or user invocations depend on; all new evals are additive files, no existing eval file is modified except where Family 11/12 extensions genuinely change `continuing-project-work`/`orchestrating-development-team` behavior (those two files' eval sets must be re-run in full, not just appended to).
