# ADR 0004: v0.2.0 scope and consolidation

## Status

Accepted — 2026-09-01 (human review of `docs/V0.2.0_MASTER_PLAN.md`, approved with adjustments)

## Context

`docs/V0.2.0_MASTER_PLAN.md` audited v0.1.0 against 12 requested skill/agent families (unit/integration tests, database/Supabase, DevSecOps, GitHub engineering, deployment/DevOps, API/backend, frontend, mobile, advanced QA, architecture, project continuity, full autonomous team) and proposed a small, gap-driven delivery rather than a family-per-skill expansion. That plan was reviewed by a human and approved with four adjustments, recorded here and applied directly to the master plan and `ROADMAP.md`:

1. `planning-deployment` moves from P1 to **P0** — a deployment-planning skill is judged load-bearing for v0.2.0 rather than deferrable, since `release-manager` currently has no deploy-planning skill at all, only release-readiness verification.
2. The database-safety model (originally folded into ADR 0005 at a coarser grain) must explicitly separate **authoring/editing/reviewing a local migration** (reversible, no extra confirmation) from **executing/applying against a real database** (high-blast-radius, gated) — see [ADR 0005](0005-database-migration-safety-model.md).
3. The DevSecOps extension to `auditing-security` must not grow into a homegrown SAST/SCA engine. Its own automation stays limited to deterministic checks (file/config presence, pattern matching); dependency-vulnerability detection defers to real ecosystem tooling where available (e.g. `npm audit`, `pip-audit`, `osv-scanner`, `cargo audit`), reporting what was actually run and its limitations rather than a home-grown vulnerability database.
4. The PR sequence is consolidated from eight PRs down to six, grouping by delivery concern instead of one PR per skill.

This ADR formalizes the resulting v0.2.0 scope so a future contributor can see what was decided and why, without re-deriving it from the master-plan document.

## Decision

### Extension-before-creation principle (carried forward from ADR 0001, made explicit as a gate)

Before proposing a new skill: check whether an existing skill's Decisions section can absorb the capability. Before proposing a new agent: check whether an existing agent's system prompt can gain a named skill pointer. v0.2.0 is the first cycle to apply this gate against concrete family requests rather than only in the abstract, and it holds for every item below:

- 4 new skills were justified only because each maps to an existing agent (`database-engineer`, `qa-engineer`, `solution-architect`, `release-manager`) that had **no dedicated skill of its own**, not because the family was requested.
- 3 extensions (`auditing-security`, `continuing-project-work`, `orchestrating-development-team`) were chosen specifically because the new capability is a natural superset of what the skill already does — a new skill would have duplicated Decisions-section logic already present.
- Zero new agents: every one of the 12 requested families maps onto one of the 10 existing agents.

### P0 — v0.2.0 (after adjustment #1 above)

1. `managing-database-migrations` (new skill → `database-engineer`)
2. `writing-automated-tests` (new skill → `qa-engineer`)
3. `reviewing-architecture` (new skill → `solution-architect`)
4. `planning-deployment` (new skill → `release-manager`) — **promoted from P1 to P0** per adjustment #1
5. `auditing-security` DevSecOps extension (dependency/SCA via real tooling, supply-chain, CI-security — see adjustment #3 and [ADR 0005](0005-database-migration-safety-model.md) is unaffected by this extension; the SAST/SCA constraint is recorded here since it governs `auditing-security`, not the database safety model)
6. `continuing-project-work` extension (module/PR/sanitization-scoped continuation routing)
7. `orchestrating-development-team` extension (role-coverage matrix + explicit token-budget rule)
8. ADR 0004 (this document) and ADR 0005 (database-migration safety model) — land before #1, since #1's safety posture depends on ADR 0005

### Zero new agents

Every family maps onto one of the 10 existing agents. A new agent is a larger structural commitment (tool scoping, safety-preload correctness per ADR 0002, namespace-collision risk) than a new skill, and none of the 12 families justify that cost this cycle.

### Mobile — separate future plugin, not a family in `ai-dev-team`

React Native/Expo (or any other genuinely new stack family) belongs in a new marketplace plugin per ADR 0001's multi-plugin shape and `ROADMAP.md`'s existing Non-goals, not bolted onto `ai-dev-team`. Not scoped for v0.2.0 in any plugin.

### Framework-specific knowledge stays references, never top-level skills

React/Next.js/Angular (and equivalent backend-framework) depth is explicitly kept as opt-in `references/*.md` content consumed by existing skills, never promoted to its own top-level skill — consistent with ADR 0001's rejection of framework-specific top-level skills.

### Mega-skills prohibited absent future evidence

No v0.2.0 skill may combine unrelated concerns to avoid adding a skill (e.g. a single "API/Backend" skill covering queues, caching, multi-tenancy, and auth was considered and rejected in the master plan as exactly the "shallow, near-duplicate coverage" ADR 0001 warns against). A mega-skill may only be proposed in a future cycle with concrete evidence — repeated real-world friction from the split, not convenience at design time — and must go through the same extension-before-creation gate as any other proposal.

## Consequences

- **Positive:** v0.2.0's skill count grows from 10 to 14 user-facing skills (not the 12-families-as-12-skills alternative that was on the table), keeping the "few excellent, composable skills" principle from ADR 0001 intact through a second cycle.
- **Positive:** promoting `planning-deployment` to P0 means all four new-skill/existing-agent gaps identified in the audit close in the same release, instead of leaving `release-manager` under-resourced for one more cycle.
- **Trade-off:** the DevSecOps automation constraint (adjustment #3) means v0.2.0 ships weaker dependency-vulnerability coverage than a bespoke scanner would provide in the ecosystems where no real tool is invoked — accepted deliberately, since a homegrown SAST/SCA engine carries a much higher false-positive/false-negative maintenance burden than composing existing, trusted tools.
- **Follow-up:** any future proposal to add a mega-skill, a new agent, or framework-specific top-level skill content must cite this ADR and present the evidence bar it requires, not just convenience.
