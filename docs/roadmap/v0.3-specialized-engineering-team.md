# v0.3 — Specialized Engineering Team

Base: `ce65381cb52c54ce618c6c43343f58e93a6d7d12`

## Mission

Evolve AI Dev Team from a capable role-based plugin into a contract-driven engineering-team orchestration framework whose specialist selection, sequencing, ownership, review loops and runtime behavior are evidence-based and testable.

## Existing roles are authoritative

Do not recreate roles already present:

- repository-explorer
- solution-architect
- frontend-engineer
- backend-engineer
- database-engineer
- qa-engineer
- security-reviewer
- code-reviewer
- debugger
- release-manager

Phase 2 may add exactly one role by default: `ui-ux-designer`. Any additional new agent requires repository evidence and explicit architectural justification.

Technology specialization belongs primarily in opt-in references/skills, not one agent per framework.

## Target pipeline

```
DISCOVER
  → ARCHITECT (when structural decision exists)
  → DESIGN (when user-facing UX/design work exists)
  → PLAN
  → CONTRACT FREEZE
  → IMPLEMENT (partitioned ownership; parallel only when independent)
  → DATABASE (when applicable)
  → TEST
  → REVIEW (code + mandatory security conditions)
  → FIX
  → VERIFY
  → targeted RE-REVIEW when findings require it
  → RELEASE / DEPLOY-PLAN when requested
  → REPORT
```

Stages remain evidence-conditional. "Full team" does not mean launch every agent.

## Required contracts

### Design handoff
User goal; information hierarchy; components; loading/empty/error/success states; responsive behavior; accessibility; design-system reuse; affected area; acceptance criteria.

### Implementation contract
Objective; bounded scope; dependencies; stable API/data/design decisions; ownership; files/areas; expected output; constraints and stop conditions.

### Agent output contract
Work performed; evidence; files changed/read; tests/checks executed; unresolved items; downstream assumptions; explicit non-actions.

### Review findings contract
Severity; evidence; affected area; reproducibility; required/optional disposition; owner; verification requirement.

### Completion handoff
Final diff/commit identity; executed validation; unresolved/deferred work; safety gates; merge/deploy actions still requiring human approval.

## Concurrency model

Synchronous by default when B consumes A's decision or artifact.

Parallel execution is allowed only after shared contracts are stable and ownership is disjoint. Examples: frontend/backend may proceed in parallel after API/design contracts freeze; architecture may not race implementation dependent on that architecture; migration design may not race backend work that needs the final schema.

One active writer per area. No overlapping file ownership.

Delegated specialist stages use synchronous delegation (`run_in_background: false`) unless genuine independent parallelism is explicitly justified and ownership is disjoint.

## Right-sizing v2

- Tiny: inline, normally 0 agents.
- Small: 0–1 specialist.
- Medium: minimum specialists needed for distinct concerns; commonly 1–3.
- Large/cross-cutting: staged team, commonly 3–6, never automatic all-agent fan-out.
- Explicit full-team request loads the orchestrator but does not override right-sizing.

## Mandatory behavioral scenarios

Runtime/static evidence must cover:
1. Small task → no unjustified fan-out.
2. UI-only → design/frontend path; no backend/database without evidence.
3. API-only → backend/review path; no designer without evidence.
4. Full-stack → design/contract freeze → partitioned implementation → QA/review → fix/verify.
5. Security-sensitive → security stage exactly once and mandatory.
6. Migration → database specialist + migration safety contract.
7. Ambiguous → evidence gathering/clarification, no premature mutation.

## Runtime evidence

For each runtime regression capture target SHA, plugin/Claude version, selected skill/agent, parent-child attribution, task packet/contract, background mode, ownership, mutations, findings, pass/fail and duplicate-stage deviations.

Start manual/workflow_dispatch. Do not make runtime-model tests a required PR gate until reproducibility, cost and false-positive rate are characterized.

## Implementation order

1. 2A contracts/orchestration foundation.
2. 2B design role and references.
3. 2C quality loop.
4. 2D CI/delivery evidence.
5. 2E runtime harness and end-to-end proof.

2E fixtures/harness design may begin early, but acceptance of the complete phase comes after 2A–2D behavior exists.

## Claude local working contract

Claude must:
- start from this branch or a child branch tied to exactly one workstream;
- inspect current repository conventions before changing architecture;
- avoid duplicating existing agents;
- keep each workstream reviewable and independently validated;
- run repository validators/tests, strict plugin validation, relevant eval checks and `git diff --check`;
- report exact commands/results and final SHA;
- never merge its own PR;
- stop rather than expand scope across workstreams without explicit evidence/approval.

## Phase exit

v0.3 is ready only when an end-to-end full-stack fixture demonstrates evidence-backed selection and sequencing through design/contract freeze, partitioned implementation, tests, review, fix/verify and final handoff, with no unjustified fan-out, duplicate specialist stage, write collision or unsupported completion/deployment claim.
