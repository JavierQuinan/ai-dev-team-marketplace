# v0.3 runtime validation handoff

## Current evidence boundary

PR #36 adds orchestration contracts and eval definitions 19–22. Static validation does not execute these scenarios against Claude. This document is a manual protocol, not the automated harness in issue #34. No runtime PASS is claimed here.

## Reproducible setup

1. Fetch the current PR head and record its full SHA; do not assume the historical head is still current. Use a clean worktree and read repository instructions.
2. Record `claude --version`, plugin manifest version, model, OS and relevant tool versions. Run repository validators and both official strict plugin validations.
3. Create disposable, synthetic fixture repositories outside the plugin checkout. Each fixture needs its own baseline commit, minimal runnable checks and documented scope. Do not use private projects or production credentials.
4. Start a fresh Claude process for each trial, loading the absolute plugin path with `--plugin-dir`. Explicitly invoke `ai-dev-team:orchestrating-development-team`; verify invocation/reference loading in the transcript. Do not use permission-bypass flags.
5. Preserve full transcripts locally, including tool-call arguments and parent/child attribution. Publish only sanitized evidence; never tokens, account identifiers or private paths.
6. Restore the fixture baseline before each independent trial. Run each scenario at least twice; retain failed and interrupted attempts. A blocked tool/authentication prompt is BLOCKED, not a behavioral PASS or FAIL.

## Scenario matrix

| Scenario | Synthetic fixture | Observable acceptance |
|---|---|---|
| Small | One existing function with a narrow defect and a regression test | Agent selection justified by scope; no unrelated fan-out |
| UI-only / eval 20 | Existing UI with a design-system sample, empty state and responsive defect | Concrete design handoff; no invented stack, API or database work |
| API-only / eval 21 | Existing endpoint, validation and tests; unchanged schema | Backend/test/review scope; no design/database stage without new evidence |
| Full-stack / eval 19 | Separate UI/API areas sharing a documented request/response interface | Contract frozen before dependent writes; disjoint ownership; concurrent work only when independent |
| Security-sensitive | Synthetic authentication/authorization change and a failing negative test | Mandatory security stage once; distinguish delegate-internal tools from duplicate parent execution |
| Migration | Disposable database schema and reversible synthetic migration | Database safety path selected; no production access or unsupported migration-success claim |
| Ambiguous / eval 22 | Preferences request with an unresolved material data/API decision | Discovery resolves the decision or dependent mutation waits; no fabricated contract freeze |

Until 2B exists, UI-only acceptance tests handoff semantics, not the existence of a designer agent. Full FIX/VERIFY and delivery behavior belongs to 2C/2D; report absent capabilities as pending, not regressions against invented implementation.

## Per-trial record

Record: scenario/trial ID; timestamp; plugin SHA/version; Claude/model/tool versions; fixture baseline SHA; exact prompt; invoked skills/references; selected agents and reasons; parent/child call IDs; `run_in_background` arguments; contracts and freeze point; READ/WRITE ownership; files actually mutated; executed checks and exit results; findings/disposition; transcript location; PASS/FAIL/BLOCKED/NOT RUN; deviations and reviewer rationale.

Observe tool events and diffs, not only the final narrative. If the trace cannot establish ordering, ownership or attribution, mark that assertion INCONCLUSIVE. Sequential implementation is valid when independence is not established; parallelism is not itself a success criterion.

An unresolved required BLOCKER prevents completion unless the user explicitly accepts a bounded deferral with residual risk and owner recorded. A deferral is not a fix or a passing verification result.
